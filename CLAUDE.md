# Goalong — guide des agents

## Où travailler
- Un worktree par sujet : `~/Developer/goalong-<sujet>-<date>`, créé depuis `origin/main`. Le checkout principal est en retard : ne pas y travailler.
- Si un dépôt local ne fetch plus (`bad object refs/heads/feat/garant-mac-20261008`), créer le worktree depuis `~/Developer/goalong-motion-placement-app-20260918`. Ne pas supprimer cette branche locale.
- Contexte projet (état, décisions, pièges) : `CONTEXT.md` du checkout principal (non versionné).

## Quatre voies
1. **Goalong Dev** (itération locale) : `make dev` construit le worktree en une app séparée qui tourne **à côté** de Goalong installé. Ne publie rien.
2. **Goalong local** (essai réel, sans GitHub) : `make local` remplace Goalong dans `/Applications` par le worktree, signé comme une release. Ne publie rien. Voir plus bas.
3. **Goalong perso** (usage quotidien du propriétaire) : `make perso` = `make local` sur un commit propre, qui garde ce commit. Sparkle n’y installe une release que si elle contient ce commit. Voir plus bas.
4. **Release** : une PR `perso` → `main` qui regroupe tout → CI → merge → Sparkle. **Merge = publication publique** : seulement quand le propriétaire dit « déploie » (ou « envoie aux clients »).

## Boucle quotidienne
Branche longue `perso`. Une demande du propriétaire = `make dev` (essayer à côté, si utile) → commit sur `perso` → **`make perso`** lancé par l’agent lui-même : une seule commande, qui teste, construit, pousse et installe (~1–2 min pour un petit changement ; échec de test = rien installé). Pas de PR par changement, pas d’attente de CI. Publier : sur « déploie », une PR `perso` → `main`, CI, merge.
- Avant `make perso`, fusionner `origin/main` dans `perso` si `main` a avancé : le build perso ne doit pas être plus ancien que la release installée (sinon l’installation est refusée).
- Une PR normale reste pour une mise en place unique (outillage, le canal perso lui-même).

## Goalong perso (`make perso`)
- Même build que `make local` (`scripts/local_try.sh`, créneau d’essai 99), mais refuse un arbre modifié et écrit commit et branche dans Info.plist (`GoalongPersoSourceCommit`). Réglages › Mises à jour affiche « Build perso · branche · sha ».
- Sparkle : la release la plus récente n’est proposée que si GitHub confirme qu’elle contient le commit (ancêtre du tag, ou PR fusionnée dans `main`). Sinon une ligne « Release X ignorée : ne contient pas ton commit <sha> » ; en cas de doute (pas poussé, réseau, limite d’API) : ignorée, nouvel essai plus tard. Jamais de retour en arrière. Une fois la PR fusionnée, la release suivante remplace le build perso.
- Code réseau compilé seulement avec `-DGOALONG_PERSO` (jamais en CI) : les releases publiques ne changent pas. Sortir du perso : réinstaller une release à la main.
- Une commande : `make check` (fichiers changés depuis le build installé) tourne à côté du build release ; un test rouge = rien installé (résumé `.build/goalong-local/tests.out`, log `tests.log`). Puis HEAD et arbre revérifiés (commit testé = commit livré), push de `perso` si GitHub ne connaît pas le commit, échange. `FILTER=Regex` comme pour `make check`.
- **Agents** : lancent `make perso` eux-mêmes après commit sur `perso` (pas de `make check` ni de push avant : il les fait). `make perso NO_INSTALL=1 OUT=/private/tmp/…` reste possible pour un essai à blanc. En cas de refus de l’installation, de retour en arrière ou d’un blocage qui refuse de quitter : s’arrêter et le signaler, ne pas contourner.
- Auto-installation (Goalong perso en marche, build avec `health.json`) : `make perso` dépose le build dans `~/Library/Application Support/LocalHistory/PersoUpdate/inbox/`. Goalong vérifie (même bundle id, build perso plus récent, signature = sa propre exigence désignée et son certificat), copie à côté de lui, échange les deux bundles d’un coup, quitte comme pour Sparkle ; le relanceur rouvre la nouvelle version et revient en arrière sans `health.json` en 45 s. Pendant un blocage verrouillé : permis, mais 1 installation par 10 min. Goalong arrêté ou build plus ancien : l’installeur (qui refuse pendant un blocage).
- **Blocage verrouillé en cours (règle de Mathis, 2026-11-22)** : un agent ne livre jamais un changement qui affaiblit un blocage verrouillé pendant qu’il tourne (garde, minuterie, mot de passe, liste, règle d’arrêt, relance, auto-installation…). Le préparer sur une branche, l’installer seulement après la fin du blocage. Les autres changements se livrent normalement.
- Aucune autre installation locale dans `/Applications` : `make install-source` garde un numéro `YYYYMMDD.HHMMSS` < `30000000.x`, que Sparkle remplace aussitôt.
- Agent launchd `ai.goalong.local-auto-deploy` (publication rapide après merge, signée sur le Mac) : seul le propriétaire le démarre (`python3 scripts/install_local_auto_deploy.py --start`). Les agents ne chargent ni ne rechargent aucun `ai.goalong.local-*`.

## Goalong local (`make local`)
- `scripts/local_try.sh` : build release, arch du Mac, sans tests (faire `make check` avant), signée avec le certificat épinglé et les droits release, Sparkle actif. Bundle id `ai.goalong.localhistory` : permissions et données réelles gardées.
- Numéro de build : créneau d’essai (tentative 99) de la release la plus récente connue (app installée et manifeste public). Sparkle ne réinstalle donc pas cette release par-dessus ; la release suivante (run plus récent) remplace l’essai normalement. Politique : `scripts/build_number_policy.sh`, test `scripts/test_build_number_policy.sh`.
- L’installation passe par `scripts/install_from_source.sh` (même identité de signature exigée, refus pendant un blocage sévère, fermeture propre, retour arrière). Refus si l’app installée est plus récente que l’essai.
- **Agents** : préférer `make perso` (commit propre et traçable). `make local` reste permis ; `NO_INSTALL=1 OUT=/private/tmp/…` = build, signe, vérifie, sans fermeture ni installation.

## Goalong Dev (`make dev`)
- App `~/Applications/Goalong Dev.app` : bundle id `ai.goalong.localhistory.dev`, processus `Goalong History Dev`, même certificat que la release (exigence désignée sans empreinte : les permissions accordées restent d’un build à l’autre). Icône DEV, point orange en barre des menus, titres « — Dev », bandeau branche · commit · données.
- Build debug incrémental dans le `.build` du worktree (le même que `make test`), signe, installe, ferme **seulement** une Goalong Dev en cours, lance via `open`. Durée de chaque étape affichée ; log `.build/goalong-dev/build.log`. Goalong installé n’est jamais fermé : enregistrement et blocage réels continuent.
- Une seule Goalong Dev à la fois : le dernier `make dev` gagne (le bandeau dit quelle branche). L’étape installation/données prend un verrou global (`~/Library/Caches/goalong-dev-install.flock`) : deux worktrees n’installent jamais en même temps. `make dev-stop` ferme Goalong Dev seulement (il attend ce verrou, pas la fin d’un build) ; `make dev-status` donne branche, commit, date, mode de données et état.
- Données : `~/Library/Application Support/LocalHistory-Dev/`, jamais `LocalHistory/`. `DATA=clone` (défaut : clone APFS des vraies données, sans clé d’appareil, chaîne signée de l’appareil réel (`seals/`, `receipts/`, `integrity-state.json`), jetons de compte, `Blocking/`, `Focus/`, sauvegardes ni sockets), `DATA=keep` (garde l’état dev ; un dossier d’un ancien `make dev`, marqueur absent ou `v2`, perd d’abord clé d’appareil, chaîne signée, jetons et sauvegardes réels ; Goalong Dev refuse de démarrer dessus avant), `DATA=fresh` (vide, nouvel utilisateur). `DATA=real` n’existe plus. Réglages lus seulement sur la ligne de commande de `make` (un `export DATA=…` du shell est ignoré).
- Blocage et Concentration de Goalong Dev sont à elle, vides par défaut. `BLOCKING=copy` copie les listes réelles sans verrou, mot de passe ni session. Le vrai blocage reste appliqué par Goalong installé.
- Coupé dans Goalong Dev : envois serveur (site, envoi quotidien, partage, Jev, vérification) sauf `SERVER=on` (bandeau orange), élément de connexion, Sparkle, migrations d’installation, lien `goalong-history://`, installation/retrait des hooks d’agents (fichiers partagés avec Goalong installé : à gérer depuis Goalong installé). Préférences : domaine propre (`ai.goalong.localhistory.dev`). Socket CLI dans `LocalHistory-Dev/runtime`.
- Première utilisation : le propriétaire accorde une fois les permissions à Goalong Dev (Accessibilité, Surveillance de l’entrée, etc.).
- **Agents** : ne lancent pas Goalong Dev sans demande du propriétaire (fenêtres, demandes de permission). Utiliser `make dev NO_LAUNCH=1 DEV_APP_DIR=/private/tmp/…` (build, signe, installe ; ni données, ni fermeture, ni lancement ; `DATA`/`BLOCKING` refusés ; bandeau « données non préparées »). Sans `DEV_APP_DIR`, cela remplace la Goalong Dev du propriétaire (refusé si elle tourne).
- Limite tant qu’aucune release ne connaît `ai.goalong.localhistory.dev` (0.6.82 et avant ; `make dev` l’annonce) : Goalong installé enregistre les fenêtres et le texte de Goalong Dev dans le vrai `LocalHistory/`, et une liste « autoriser seulement » bloque Goalong Dev.
- Braise agit sur les vrais écrans (gamma global) : Braise actif dans les deux apps = conflit d’affichage. Le clone n’emporte pas l’état gamma de Goalong installé (`Braise/display-recovery*`).
- Non isolé ou non vérifié : trousseau (sans groupe partagé, séparation par bundle id non vérifiée).

## Interdits
- Jamais forcer la fermeture : un blocage actif peut refuser de quitter ; le résoudre dans l’app.
- Ne pas modifier `/Applications/Goalong History.app` autrement que par `make perso` / `make local` (garde-fous de `scripts/install_from_source.sh` : même identité de signature, refus pendant un blocage sévère, fermeture propre, retour arrière), ni le trousseau, ni `blocking.json` à la main app ouverte.
- Migration de données, réglages `*_FORCE` et `*_ALLOW_*` : le propriétaire seulement.

## Vérifications
- Jamais `swift test` nu. Trois commandes, toutes en HOME jetable (`scripts/run_swift_tests.sh`) : `make check` (boucle rapide : fichiers changés non commités, sinon depuis le commit perso installé, sinon vs `origin/main` ; un fichier de l’app lance les classes de test qui citent ses types + `GallerySmokeTests`/`BlockingGuardTests` (cible App entière au-delà de 60 classes) ; un script lance son `scripts/test_*` ; ou `FILTER=Regex` ; sans les 5 tests lents ni les budgets de durée (`make test`) ; vert = vert, sortie courte, log `.build/goalong-check/last.log`), `make test` (suite complète puis rapport des tests ignorés ; un skip absent de `scripts/expected_skips.txt` fait échouer), `make test-ui` (rendus et tests AX opt-in, `GOALONG_*_SNAPSHOTS` / `*_UI_TESTS`, sans fenêtre visible ; dit si l’écran est verrouillé ; PNG dans `/tmp/goalong-test-ui-*`). Un test opt-in nouveau doit entrer dans `expected_skips.txt` (`python3 scripts/skip_report.py LOG --emit-allowlist` aide). Les cibles App et Ambiance chargent le hook `GoalongHeadlessTestSupport`, qui supprime à la sortie les plists `UserDefaults(suiteName:)` créés par la course (jamais ceux qui existaient) ; `scripts/clean_leaked_test_prefs.sh [--dry-run|--delete] [--include-other-test-suites]` nettoie les anciennes fuites (`goalong-auto-consent-*` seulement par défaut). Puis `make audit`.
- Scripts Goalong Dev : `bash scripts/test_dev_app.sh` (sans build ni lancement ; lancé par `make test` et la CI). Identité dev/release : `bash scripts/test_stable_release_identity.sh` (clé de signature requise).
- Après ajout d’un fichier Swift dans l’app : `python3 scripts/generate_support_source_allowlist.py`.
- Toute nouvelle sortie réseau : `docs/NETWORK.md` et `scripts/generate_security_artifacts.py`.

## Tests invisibles (règle de Mathis, 2026-10-26)
- Aucune fenêtre de test ne doit apparaître sur l’écran du Mac ni prendre le focus. Jamais.
- Lancer les tests sur `ssh ci` quand c’est possible. `ci` est Linux : les tests AppKit, la galerie et les rendus restent sur le Mac.
- Sur le Mac, jamais au premier plan : `open -g -j` (jamais `open` seul), ni `activate`, processus `.prohibited`/`.accessory`, fenêtres à alpha 0, hors écran ou en bas à droite, cachées ou réduites, sans focus clavier. Fermer chaque fenêtre et chaque instance lancée à la fin.
- Garanti par construction : `Tests/GoalongHeadlessTestSupport` (fenêtres à alpha réel 0 vérifié à chaque mise à l’écran, sans animation, éléments de barre des menus cachés, processus `.prohibited`, ni activation ni ouverture d’URL/app ; un chien de garde interroge le serveur de fenêtres toutes les 100 ms, cache toute fenêtre visible, écrit `[headless-tests] VISIBLE` et la course sort en 1). En plus, `scripts/window_guard.swift` surveille `make check|test|test-ui` et `make gallery` toutes les 50 ms : fenêtre visible ou focus pris = processus tué, course en échec. Test : `HeadlessWindowGuardTests`. Pour voir les fenêtres : `GOALONG_TESTS_VISIBLE=1` (coupe tout).
